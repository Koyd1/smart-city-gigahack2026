Дата проверки: 26 сентября 2026 года.

## Итог

Приложение собирается и основные сценарии работают в dev-режиме: публичный чат создаёт сессию, RAG возвращает ответ, администратор входит в систему, видит базу знаний, feedback, шаблоны, FAQ и health dashboard. Миграции актуальны.

Проблема загрузки документов устранена после аудита: MinIO удалён, файлы хранятся в PostgreSQL.

## P0 — исправить до публикации

### 1. Немедленно отозвать ngrok authtoken

В отслеживаемом Git файле `DEMO_RUNBOOK.md:36` записан настоящий `ngrok config add-authtoken ...`.

Что сделать:

1. Отозвать токен в ngrok dashboard и выпустить новый.
2. Удалить токен из файла и из истории Git (`git filter-repo` или BFG), если репозиторий когда-либо отправлялся на сервер.
3. Добавить secret scanning в CI: Gitleaks или TruffleHog, а для GitHub — secret scanning/push protection.
4. В документации оставить только `ngrok config add-authtoken <YOUR_TOKEN>`.

### 2. Обновить уязвимые frontend-зависимости

`npm audit` нашёл 9 уязвимостей: 3 critical, 4 high, 1 moderate и 1 low.

Минимальный срочный набор:

| Пакет | Сейчас | Цель | Причина |
|---|---:|---:|---|
| `next` | 16.1.7 | 16.3.6 | В текущей версии есть critical/high advisories, включая RCE, SSRF, middleware bypass и DoS. |
| `next-auth` | 5.0.0-beta.30 | 5.0.0-beta.32 или новее совместимой линии | Critical fail-open/auth normalization advisories затрагивают версии до beta.31. |
| `postcss` | 8.5.8 | 8.5.28 | Закрывает path traversal/file disclosure advisories. |
| lockfile/transitive packages | текущие | пересобрать после обновления | Уязвимы `sharp`, `lodash`, `nanoid`, `baseline-browser-mapping`, `esbuild`. |

После обновления: `npm audit`, typecheck, production build, login/admin/public-session smoke и проверка proxy redirects.

Ссылки: [Next.js RCE advisory](https://github.com/advisories/GHSA-p293-qw3h-jr36), [NextAuth fail-open advisory](https://github.com/advisories/GHSA-8fpg-xm3f-6cx3).

### 3. Устранено: удалить `minio/minio:latest`

`docker-compose.yml:3` использует плавающий `minio/minio:latest`. Сейчас этот тег запускает MinIO AIStor. Логи сообщают: `No valid license found` и `All S3 operations are denied`. Smoke-загрузка получила `AccessDenied` на `ListBuckets` и вернула UI ошибку `502`.

Текущий healthcheck проверяет только живой HTTP-процесс и поэтому показывает контейнер как healthy, хотя основная функция не работает.

Решение, применённое после аудита:

- MinIO и `boto3` удалены из приложения и Docker Compose.
- Файл сохраняется вместе с метаданными в `knowledge_files.binary_content`.
- Лимит 15 МБ оставлен; при существенном росте объёма следует перейти на managed S3/R2/B2.
- Старые записи без `binary_content` удаляются миграцией, поскольку восстановить их без object storage невозможно.

Официальный репозиторий MinIO сообщает, что Community Edition теперь распространяется только как source code; репозиторий архивирован, а старые бинарные релизы не поддерживаются: [MinIO README](https://github.com/minio/minio/blob/master/README.md), [releases](https://github.com/minio/minio/releases).

### 4. Исключить пересечение анонимных сессий

`frontend/lib/session.ts:52` создаёт одного пользователя `guest@public.local` для всех посетителей. `frontend/app/api/session/public/bootstrap/route.ts:43-45` затем ищет любую пустую активную сессию этого общего пользователя.

Два новых посетителя, пришедшие почти одновременно, могут получить один и тот же `sessionId` и подписанную cookie. После первого сообщения второй посетитель сможет открыть ту же историю. Это риск утечки переписки.

Что сделать:

- Для нового браузера всегда создавать новую анонимную сессию; не вызывать `findEmptyActiveSession` для общего guest user.
- Лучше создавать отдельный anonymous principal UUID на браузер и связывать его с подписанной HttpOnly cookie.
- Добавить конкурентный тест: два чистых browser contexts не должны получать одинаковый session ID и видеть сообщения друг друга.

## P1 — высокий приоритет

### 5. Исправить local/prod redirects и конфигурацию origin

Production build успешно стартует, но локальный сценарий из runbook ломается:

- `/chat` перенаправляет на `/api/session/public/bootstrap`, а тот строит абсолютный URL от `request.url` и выдаёт `http://0.0.0.0:3000/chat?...`.
- `public_session` получает `Secure`, потому что `NODE_ENV=production`, хотя runbook открывает приложение по HTTP.
- Login перенаправил на старый offline ngrok URL из `.env`.

Что сделать:

- Разделить `.env.development.local` и production env; не хранить временный tunnel URL как общий `NEXTAUTH_URL`.
- Строить redirects от доверенного public origin или корректных `Forwarded`/`X-Forwarded-*` headers.
- Выбирать `secure` по реальной HTTPS-схеме/public origin, а не только по `NODE_ENV`.
- Добавить smoke для `npm run start -H 0.0.0.0`: home → public chat и login → admin должны оставаться на ожидаемом origin.

### 6. Завершить переход от HR-бота к муниципальному CIVIS

UI обещает муниципальные решения и услуги, но backend всё ещё использует `You are an HR assistant` (`backend/app/core/chat_prompt.py:5`), no-context ответ просит загрузить HR-документы (`backend/app/api/v1/chat.py:107-112`), README и package metadata называют продукт HR Bot. В production data находятся документы Orange/HR, FAQ про отпуск и prompt templates для сотрудников компании.

Это влияет на ответы, источники, аналитику и доверие пользователя.

Что сделать:

- Утвердить одну предметную область: муниципальный CIVIS или HR assistant.
- Если остаётся CIVIS: заменить system prompt, FAQ, шаблоны, seed, документацию и knowledge corpus на муниципальные данные.
- Явно требовать ответ на языке вопроса: Romanian/Russian/English.
- Локализовать no-context и model-failure ответы; сейчас они всегда на русском.
- Удалить опечатки в шаблонах (`уточified`) и версионировать prompts как код/данные с review.

### 7. Не подменять сбой embeddings фиктивными векторами

`backend/app/core/embedder.py:31-56` при отсутствии ключа или любой ошибке OpenAI генерирует SHA-256-векторы и продолжает поиск. Пользователь получает правдоподобный ответ на случайно найденном контексте, а ошибка провайдера скрывается.

Что сделать:

- В production возвращать явный `503`/degraded response и не вызывать генерацию ответа на фиктивном retrieval.
- Оставить fake embedder только как явно включаемый test stub.
- Добавить timeout, ограниченные retries с jitter и метрику ошибок embeddings.

### 8. Добавить rate limiting и бюджетные ограничения

Public chat доступен без входа и вызывает embeddings, chat model и иногда judge. Ограничений по IP/session, concurrent streams и дневному бюджету в коде нет. Login также не защищён от перебора.

Что сделать:

- Redis token bucket: отдельные лимиты для login, public bootstrap, chat и feedback.
- Ограничить число одновременных stream на session/IP.
- Добавить дневной/месячный budget circuit breaker и понятный ответ пользователю.
- Ограничить размер всей истории запроса по токенам; сейчас проверяются только 50 сообщений × 6000 символов.

### 9. Упростить и ускорить health dashboard

`backend/app/api/v1/health.py:28-33` последовательно делает внешний embedding request, Redis check, DB counts и большой набор аналитических SQL-запросов. Dashboard регулярно повторяет этот дорогой запрос. При загрузке UI сначала показывает `EȘEC` и нулевые метрики, хотя данные ещё не пришли.

Что сделать:

- Разделить `/live`, `/ready` и `/admin/metrics`.
- Не вызывать платный embedding API на каждый UI poll; кэшировать deep check на 1–5 минут или проверять только доступность модели по расписанию.
- Свести аналитику в несколько SQL-запросов/materialized aggregates и добавить индексы после `EXPLAIN ANALYZE`.
- Параллелить независимые проверки с отдельными DB sessions там, где это безопасно.
- В UI показывать skeleton/loading state, затем status; не показывать `EȘEC` до завершения запроса.

### 10. Сделать ingestion надёжным

Индексирование запускается через FastAPI `BackgroundTasks`. При рестарте процесса job теряется; retry/dead-letter очереди нет. Состояние может зависнуть в `PROCESSING`.

Что сделать:

- Вынести ingestion в Redis-backed worker: Arq, Dramatiq, RQ или Celery.
- Добавить idempotency, retries, dead-letter state, heartbeat и восстановление зависших jobs.
- Сохранять original bytes в один выбранный источник истины. Сейчас upload требует S3, но старые записи могут скачиваться из `binary_content` PostgreSQL, что создаёт двойную модель хранения.

## Более современный OpenAI-подход

Код использует `chat.completions`. OpenAI рекомендует Responses API для новых интеграций и постепенную миграцию существующих flows. Для этого проекта разумен incremental rollout:

1. Сначала перенести hallucination judge на Responses API + Structured Outputs.
2. Затем перенести основной streaming chat и адаптировать typed streaming events.
3. Оставить историю диалога в собственной БД или осознанно выбрать `previous_response_id`; не смешивать обе модели состояния без необходимости.
4. Для муниципальных документов сохранить собственный pgvector pipeline, пока evals не покажут пользу hosted file search.
5. Сравнить answer quality, retrieval faithfulness, latency, token usage и cost на фиксированном наборе вопросов до переключения трафика.

Официальная инструкция: [Migrate to the Responses API](https://developers.openai.com/api/docs/guides/migrate-to-responses).

## Текущий способ локального запуска

Backend и Redis запущены через Docker Compose. Frontend оставлен в dev-режиме с локальными origin overrides:

```bash
cd frontend
NEXTAUTH_URL=http://127.0.0.1:3000 \
WEB_ORIGIN=http://127.0.0.1:3000 \
npm run dev -- -H 127.0.0.1 -p 3000
```

Открывать: `http://127.0.0.1:3000`.

Документы до 15 МБ загружаются в PostgreSQL без отдельного object storage.
